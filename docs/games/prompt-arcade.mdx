---
title: Prompt Arcade architecture
description: 'Parallel player-authored generation, standardized scoring, and browser containment'
---

Prompt Arcade is an official Xup game in which every active player authors one
mini-game prompt. Each accepted prompt starts its own generation job immediately;
there is no vote, top-N filter, or unrelated fallback game.

## Lifecycle

```text
lobby -> prompting -> generating -> countdown -> playing -> roundResults
                       ^                                      |
                       |--------------------------------------|
                                                               -> complete
```

Starting a session snapshots the active room members into at most 30 prompt
entries. Late joiners can be enrolled while prompts are still being collected,
but a player is never silently dropped after submitting.

An entry advances through observable stages:

```text
writing -> queued -> generating -> validating -> ready -> played
                                  -> repairing -> ready
                                               -> needsRevision -> queued
```

The room view derives its aggregate progress from the bounded set of entry rows.
Stage changes are real state transitions; the client never invents a token-level
generation percentage. The owner can start the playlist after
`min(3, participantCount)` games are ready. Remaining jobs continue in the
background and enter the playlist when they become ready.

Unresolved work is never dropped automatically. If every playable game has
finished and only `writing` or `needsRevision` entries remain, the owner gets an
explicit, confirmed option to mark those entries withdrawn and finish the
stalled playlist. The action is unavailable while any game is ready or any
generation attempt is still live.

## Generation contract

A Convex Node action calls the OpenAI Responses API with strict Structured
Outputs. The response contains:

- a title, interpretation, and player instructions;
- a bounded duration;
- one scoring mode: `speed`, `quality`, or `qualityAndSpeed`;
- standalone JavaScript that registers one game with the trusted runtime.

The server validates the structured fields and rejects dangerous or unsupported
browser capabilities. It makes at most one repair request. A second failure
puts only that player's entry into `needsRevision`, where the player can edit
and regenerate it. Valid code is stored in Convex file storage and is only
resolved for an authorized room member during the active round.

The resolved storage URL is bearer-style: anyone who obtains it can reuse it
while the stored file exists. Generated source is therefore treated as
non-sensitive, may never contain credentials or player data, and is not exposed
by the room query before its round. One hour after the playlist completes, a
guarded cleanup deletes the stored code blobs while retaining artifact metadata
for diagnostics.

## Standardized scoring

Generated code cannot award points. It may finish once with a normalized
`quality` value from 0 through 1 and optional display-only metric data. Convex
measures elapsed time from the authoritative round start and clamps every
number before applying the selected formula:

| Mode | Score |
| --- | --- |
| `speed` | `round(1000 * speed)` |
| `quality` | `round(1000 * quality)` |
| `qualityAndSpeed` | `round(750 * quality + 250 * speed)` |

`speed` is `clamp(1 - elapsed / duration, 0, 1)`. Timeouts score zero. This
keeps arbitrary interaction mechanics compatible with one leaderboard while
leaving final timing and scoring authority on the backend.

The normalized quality value necessarily originates in the generated browser
game. A determined player could forge that input, so this MVP is an
honest-client scoring system for the stated internal-use environment, not an
anti-cheat system. Convex still owns membership checks, round identity, elapsed
time, clamping, idempotency, and the final formula.

## Browser boundary

The React application downloads the current artifact, then passes it into an
opaque-origin iframe with only `allow-scripts`. A trusted static runner owns the
DOM mount and completion bridge. The iframe receives no guest token, Convex
client, OpenAI key, or parent application state.

The iframe document applies a restrictive Content Security Policy that blocks
in-document network connections and external assets. The iframe sandbox blocks
forms, popups, and escape into the parent or top-level page. The validator
rejects direct navigation APIs, while the runner cancels ordinary links and
form submissions. Same-frame navigation cannot be completely prohibited
against deliberately obfuscated JavaScript, so navigation rejection is a
defense-in-depth check rather than a hard security boundary. Messages are
accepted only from the exact iframe window and must carry a per-mount random
nonce. For normal event-driven code, removing the iframe ends the round. This is
lightweight containment for an internal, good-actor environment; generated code
is still treated as untrusted at the application boundary.

The iframe boundary is capability containment, not a hard CPU quota. A
synchronous infinite loop can still monopolize a browser renderer before the
parent timeout runs. Strong hostile-code isolation would require a worker-based
rendering contract or a separately hosted execution boundary; Prompt Arcade's
MVP instead combines strict generation instructions, static rejection, and the
internal-use threat model.

## Capacity and operations

Each submission runs as an independent direct Node action and writes to its own
artifact row, so one slow generation does not serialize or overwrite another
player's progress. The default S16 deployment class supports 64 concurrent Node
actions, enough for the game's 30-player cap; short scheduled mutations remain
reserved for stale-job watchdogs and round timers. Actual throughput is still
bounded by the model provider's rate limits. A rate limit or transient provider
failure gets at most two bounded retries, honoring `Retry-After` when present and
otherwise using jittered backoff; player actions remain independent and
parallel. The UI exposes queued versus generating states so backpressure is
visible instead of disguised as progress.

Configure generation with Convex deployment environment variables:

```bash
pnpm exec convex env set OPENAI_API_KEY '<your-api-key>'
pnpm exec convex env set OPENAI_PROMPT_ARCADE_MODEL '<responses-api-model-id>'
```

The owner cannot start Prompt Arcade if either value is missing or blank. Before
enabling it in a deployment, run one real generation with that exact model and a
30-request burst against the deployment's OpenAI project limits.

## Admin playtest bots

The owner-only Playtest page can fill a Prompt Arcade room to at most 30 active
members. Every bot is provisioned through the shared `playtestRuns` and
`playtestBots` infrastructure, then receives game-specific state in
`promptArcadePlaytestBotStates`.

During prompt collection, each bot composes a bounded randomized concept from
separate theme, mechanic, twist, and winning-criteria catalogs. The resulting
text always includes an explicit `Winning criteria:` clause and uses the same
generation and validation pipeline as a human prompt. A failed generation gets
a different deterministic combination on its next revision attempt.

Bots cannot execute arbitrary generated browser code on the backend. During a
playing round, the adapter instead schedules a varied completion time and
quality value, then submits that simulated result through the authoritative
Prompt Arcade scoring function. Human browser sessions still exercise the real
iframe runtime. Removing the playtest run deactivates bot memberships, clears
their presence, and withdraws any bot-authored work that has not played yet.

Adding many Prompt Arcade bots starts one model generation per bot and therefore
uses the configured provider quota and generation budget.

## Browser smoke test

The unit suite validates the runtime message contract, CSP/sandbox attributes,
authorization, lifecycle timing, scoring, and generated-code validation. Before
shipping a deployment, also exercise the real browser boundary:

1. Start Prompt Arcade with two browser sessions and submit two different prompts.
2. Confirm both per-player stages advance independently and the room progress updates.
3. Play a generated pointer or keyboard game through completion, then let another time out.
4. Confirm the iframe cannot fetch an external URL or open a popup, results submit once,
   and the playlist advances to the next ready artifact.
